- 游戏随机效果采用 xorshift32，默认种子 `0x4D415249`；算法、零种子规则和固定向量见样例说明。没有承诺标准库 `random`，没有修改解释器哈希随机源。

逻辑回归把原项目 `C:/VD/Projects/mario/index.html` 作为只读来源。原件 SHA-256：`53b556316bbc25a5c2c80b046be836dbaaea8aa5c25e85a2cf5f29a4b4bc9ef1`。原版提取器只屏蔽外围 UI/声音/存储副作用并替换随机源，普通验收读取已归档的 `reference.json`。比较游戏/角色状态、全部敌人、已用砖块/金币、粒子总数及前两项样本、全部飘字及 RNG 状态，浮点容差 `1e-7`。

浏览器数值回放每个原生动画回调只推进一个物理步；检查点观测、最终绘图构建及提交分别占用独立回调，仍受相同原生额度保护。它验证嵌入式解释器中的整关状态一致性，不是人工键盘通关、生产调度器持续绘制全关或 120 Hz 实时性能证据。实际页面的固定时钟、软额度与真实输入另有独立检查。

实际页面另外通过原生键盘、鼠标/指针验证开始、移动、跳跃、暂停、重开、捕获释放和后台恢复；有测试驱动断言真实点击的 `isTrusted`。游戏页面本身不使用测试驱动的 JavaScript。

## 帧调度、缓存与测量

固定物理步长为 `1/120` 秒，dt 最大 50 ms，每帧最多六步。实际页面有 2 ms 物理工作软额度：执行完当前步后检查，超载丢弃剩余积压并记录 `dropped_s`，不会在恢复后补算整段后台时间。关闭墙钟软额度的确定性测试比较 30/60/120 Hz 输入采样；另用注入时钟验证软额度丢弃。这个原型在慢机器/Debug 负载下可能出现游戏时间慢于墙钟的情况，不能宣称持续稳定 120 Hz 物理。

构建批次和提交分布到两个原生动画回调，绘图上限 30 Hz，忙时延后绘图；最多保留一个待提交批次。静态状态不重复绘制，HUD 每 250 ms 准备一次，每回调最多写一个 DOM 文本节点。失焦、隐藏及输入 epoch 变化清输入、暂停游戏并重置物理基准。

只使用页面画布及七个缓存资源。7040 像素静态地形以四分之一比例存入 1760×152 表面；角色、敌人、金币及砖块缓存复用。可见区域裁剪，最多模拟 128 粒子、32 飘字，一帧最多画 24 粒子。远景、地面装饰、角色步态、旗帜形状和粒子淡出做了简化，关卡碰撞几何和计分维持原版。

页面记录物理、构建、提交、包含 HUD 的回调主体耗时，生命周期峰值、最近 32 个样本的 p95、帧间隔、步数、绘图命令/字节/像素估算和积压丢弃量。`native_ms` 仅为 Blink 预检/原生提交，不含 Python 构建、Chrome 转换、回调结束后的宿主清理或最终 GPU 栅格。

## 本阶段运行时改动与额度评估

1. 增加 `Batch.fill_rects`：只接受精确 list/tuple 和精确五元 tuple 行 `(x,y,w,h,hex_color)`，不执行任意迭代器或数字转换。展开为原有颜色/矩形命令，继续计入 4096 命令、512 KiB、绘图窗口和像素额度；无新 Blink 操作。尾行错误整组不修改批次，每 64 行及返回前检查停止/时间，已提交批次仍不可修改。原生像素、费用、非法类型、原子拒绝、封存、聚合数量/字节及停止/撤权后不能提交均有回归。
2. 纯命令构建只检查当前执行、时间和已锁存停止原因；不产生 DOM/像素效果，完整页面策略与资源校验仍在提交前后和原生执行期间执行。执行外、清理期或失效模块不能构建。
3. 追踪器每次函数调用/返回仍检查时间和锁存状态；昂贵页面策略最多相隔 64 个追踪事件检查一次，调用/返回也计数。桥接、执行入口/结束继续完整检查。这样避免生成器每次恢复都重复执行完整站点策略，未关闭循环/递归/原生调用前后的预算保护。
4. Renderer 启动开关不可变，缓存“放开页面限制”的解析结果；来源判断和 Renderer 沙箱语义不变。
5. CPython 私有核心使用 `optimize_speed`，Chromium/适配层仍为 Debug；保留符号、常规断言和链接诊断，没有关闭 GHASH/PDB 检查。

总方案把 **8/200/250 ms** 标记为待阶段四/七评估的试验值。经过缓存、物理裁剪、分帧提交及追踪优化，8 ms 在本机 Debug 下仍有偶发致命停止，既发生在实际游玩，也发生在完整状态观测中。本阶段将单帧协作式保护**明确改为 16 ms**，同步完整单次准入预留、致命诊断、设置说明和边界测试。200 ms/秒帧子额度、250 ms/秒交互总额度、初始化/清理、输入/输出/DOM/绘图/资源额度全部维持原值。窗口不足仍延后，单次超限仍锁存停止；不是持续占用 16 ms 的许可，也不构成硬实时或内存隔离。

当前测试机器为 Windows x64、AMD Ryzen 7 5825U、component Debug，浏览器驱动使用 headless 软件绘制且保留 Renderer 沙箱。首次字体/缓存复制在初始化完成；原生冷提交曾测得约 36–46 ms，预热后约 2–3 ms。该数据和页面自测值不能替代阶段七的 Release/GPU/长时间人工游玩分析。

16 ms 下的首次统一验收仍记录过一次开始游玩后的致命帧超限，已有结果不支持宣称该问题已根治。同一实现的独立复查 24 项全部通过；记录保留在证据目录。当前单调墙钟计时会包含线程被调度离开的时间，失败日志不足以区分该次原生工作和系统调度的耗时，根因尚未确定。没有再次提高上限、重置锁存状态或在脚本中自动重试该失败；Debug 的间歇停止继续列为阶段七的稳定性问题。
